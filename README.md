# Музей несбывшихся планов

React + Vite + React Router (клиент), Express + SQLite (сервер). Данные в `data/museum-v3.db`.

Отдельный технический план для идеи: [AI Project Architect](ARCHITECT.md).

## Запуск
    cp .env.example .env
    npm install
    npm run dev                                  # сайт :5173, API :3001
    npm run build && node --env-file=.env server/index.js   # продакшен на :3001
    docker compose up -d --build                 # или Docker

## Страницы
`/` главная, `/exhibition` экспозиция, `/idea/:id` идея, `/submit` сдать идею, `/halls` залы сходств, `/mix` сочетания, `/login`, `/register`, `/profile`.

## Аккаунты
Регистрация по имени, почте и паролю. Пароли хранятся как scrypt-хэш с солью, сессии лежат в SQLite (в куке только случайный токен, в базе его хэш; HttpOnly, SameSite=Lax, 30 дней). Читать могут все, писать, лайкать и обращаться к ИИ только вошедшие. Идею и продолжение можно публиковать анонимно, имя сохраняется в базе, но не показывается. Три жалобы от разных аккаунтов скрывают идею.

### Назначение модератора

Владение почтой при регистрации не проверяется, поэтому `ADMIN_EMAIL` больше не выдаёт права. По умолчанию модераторов нет; существующие аккаунты и схема базы сохраняются. Оператор сервера должен самостоятельно проверить личность и владение уже созданным аккаунтом.

1. Владелец входит по защищённому соединению и открывает `/api/auth/me`; поле `user.id` содержит ID аккаунта. Оператор независимо подтверждает, что ID принадлежит нужному человеку, или проверяет его через доверенный административный доступ к базе.
2. Оператор указывает проверенные существующие ID в защищённой конфигурации сервера, например `ADMIN_USER_IDS=1,2`, и перезапускает сервер. При первоначальном назначении несуществующие или некорректные ID не допускаются: сервер откажется запускаться. Прежний `ADMIN_EMAIL` не даёт привилегий.
3. Если первоначальное назначение ещё не выполнено и в базе нет администратора, сервер назначит указанные аккаунты администраторами и запишет это в журнал. Метка в SQLite запрещает повторное назначение при следующих запусках, даже если в базе больше не окажется администратора. Затем удалите `ADMIN_USER_IDS` из конфигурации. Роли сохраняются в SQLite; удаление настройки не отзывает их. Последующие назначения и отзыв выполняются через `/admin` другим администратором. Последнего администратора понизить нельзя.

При первом запуске выполняется транзакционная миграция: существующие пользователи получают роль `user`, аккаунты, идеи и сессии сохраняются. Все существующие аккаунты считаются активными: отдельного признака отключения пока нет. Сделайте резервную копию базы средствами SQLite перед развёртыванием. ID могут использоваться повторно после удаления аккаунта или замены базы. Ограничьте доступ к конфигурации сервера; не оставляйте в ней старые ID.

### Восстановление администратора

Если администраторов в базе больше нет, владелец сервера должен остановить приложение, создать резервную копию базы средствами SQLite, независимо проверить владельца и ID существующего аккаунта и из защищённой консоли сервера выполнить `node scripts/recover-admin.js --db <абсолютный-путь-к-базе> --user-id <проверенный-ID>`. Скрипт работает только с существующей базой и откажет, если в ней уже есть администратор или аккаунт отсутствует. Назначение и системная запись в журнал выполняются одной транзакцией. После проверки удалите устаревший `ADMIN_USER_IDS` из настроек и запустите сервер. Публичного API восстановления нет; ограничьте доступ к файлу базы и консоли сервера.

Старую базу `museum.db` версии 2 перенести нельзя: структура изменилась, файл `museum-v3.db` создаётся заново.
